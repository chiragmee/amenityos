# AmenityOS — Agent Spec

Describes the reasoning pipeline behind the voice/text booking flow and
the AI Assistant screen. **Not implemented in this pass** — the frontend
currently simulates this pipeline with a timed 4-step animation and canned
scenario data; this document is what that simulation stands in for.

## Design stance: one orchestrator, not a multi-agent framework

Per instruction, no multi-agent framework and no LangChain absent a
compelling reason. The booking pipeline is a fixed sequence of
deterministic checks plus exactly one or two points where an LLM call is
actually needed (intent extraction, and free-text guideline
interpretation). That's a single Python function calling Gemini directly
and calling plain-code tools in between — not a graph of autonomous
agents. Revisit this stance only if a real requirement emerges that a
single orchestrator can't express (none has, from the design handoff).

## The pipeline

Mirrors the frontend's 4-step checklist exactly, because that checklist
*is* the product's description of the pipeline:

```
1. Understand request     — Gemini: utterance -> structured intent
2. Check availability     — plain code: availability engine (backend-spec.md)
3. Check booking rules    — plain code (structured rules) + Gemini
                             (free-text guidelines interpretation, only if
                             the amenity has guidelines that structured
                             fields don't already cover)
4. Book                   — plain code: transactional booking + credit
                             ledger + access pass issuance
```

Steps 2 and 4 never call an LLM — they're exactly the deterministic
engines in `backend-spec.md`. Step 1 always calls Gemini. Step 3 calls
Gemini only when needed (see below); most requests should resolve step 3
without a model call once schedule/capacity/eligibility are structured
fields.

### Step 1 — Intent extraction

Input: raw utterance (from Whisper transcript or typed text).
Output (structured, via Gemini function-calling / JSON mode):

```
{
  amenity_hint: string | null,      // name or description, may be vague
  date: string | null,              // resolved relative to "now"
  start_time: string | null,
  duration_minutes: number | null,
  attendees: number | null,
  intent: "book" | "cancel" | "check_availability" | "unclear"
}
```

If `amenity_hint` doesn't match an amenity name exactly, resolve it via
the Qdrant semantic search tool (`search_amenities`, see `tool-spec.md`)
rather than asking Gemini to guess an ID — keeps the model out of the
business of knowing the catalog.

If required fields are missing and can't be reasonably defaulted, the
orchestrator should ask a clarifying question rather than guess — the
design handoff has no clarifying-question UI yet, so this is a known gap
between the current frontend simulation and the real pipeline; flag it
rather than silently defaulting fields that materially change what gets
booked (time, attendee count).

### Step 2 — Availability

Pure lookup against the availability engine. No model involvement. If the
exact requested slot is busy, gather N valid alternatives (same amenity,
nearby times; or same time, other amenities that fit) — this is exactly
what the "Slot unavailable" and "Capacity exceeded" Assistant scenarios
render as an options list.

### Step 3 — Rules

Structured checks (capacity, frequency, max-active-bookings, eligibility)
run in plain code first and short-circuit to a block if any fail. Only if
those pass does the orchestrator consult the amenity's free-text
`guidelines` field via Gemini, asking a narrow yes/no-per-rule question:
"does this request violate any of these rules: {guidelines}? Request:
{structured intent}." This is also what powers the Admin screen's
"N rules parsed · 0 conflicts" indicator — parsing guidelines into a rule
count is a Gemini call made when guidelines are saved, not at booking
time, so booking-time checks stay fast.

### Step 4 — Booking

Deterministic: credit check → transactional insert (booking + ledger row)
→ access pass issuance. Matches `backend-spec.md` exactly. If a credit
check fails here (race with another concurrent booking), fail closed —
matches the "Insufficient credits" scenario's guarantee that a failed
booking never touches credits.

## Response generation

After the pipeline resolves (booked / options offered / blocked), a final
short Gemini call turns the structured outcome into the human-readable
`agentText` shown in the UI — the model is used for phrasing, not for
deciding the outcome. This keeps the actual booking decision auditable and
independent of model variance; the `trace` line shown in the UI is built
from the deterministic steps directly, not generated by the model, so it
stays trustworthy as a debug artifact.

## Mapping to the Assistant screen's four scenarios

| Scenario | Where it's decided |
|---|---|
| Slot unavailable | Step 2 (availability engine) |
| Paid amenity (confirm before charging) | Step 4 — always require explicit confirmation when `costCredits > 0`, surfaced as the `hasActions`/primary-secondary pattern in the UI |
| Insufficient credits | Step 4 credit check, before any DB write |
| Capacity exceeded | Step 3 (structured capacity rule) |

None of these require branching agent logic — they're outcomes of the
same four-step pipeline, which is the reason a single orchestrator
suffices instead of a per-scenario agent.

## Confirmation policy

Any booking with `costCredits > 0` requires an explicit user confirmation
action before step 4 executes, even if every check passes — matches the
"paid" scenario's `ask` sub-state and its trace line ("confirmation
required by policy"). Free bookings execute immediately once checks pass.

## What's deliberately not built yet

- Multi-turn conversation memory beyond a single request/response — the
  Assistant screen shows one exchange at a time; extending to a real
  chat history is future scope, not implied by the current design.
- Clarifying-question flow when intent extraction is ambiguous (noted
  above as a gap).
- Any autonomous/background agent behavior (e.g. proactively suggesting
  bookings) — everything here is reactive to a single user request.
